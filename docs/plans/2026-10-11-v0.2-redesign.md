# Yuyin v0.2 重新设计

**日期：** 2026-10-11
**范围：** 审查 v0.1 全部代码后重写 Core / Local / Cloud / App 四层。v0.1 源码备份在 `.backup/v0.1/`（不进 git）。

## 1. v0.1 审查结论

| # | 问题 | 后果 |
|---|------|------|
| 1 | 每个麦克风 buffer 各起一个 `Task` 调 `ingest` | Swift 不保证这些 Task 的执行顺序，音频帧可能乱序送进识别器 |
| 2 | partial 文本通过 `Task { @MainActor … markPartial }` 回调送达 | 判句之后才到的旧文本会生成「幽灵句」或覆盖新句 |
| 3 | `stop()` 先取消纠错任务、关闭引擎，再立刻保存会议 | 最后一两句以「纠错中 / 未纠错」写入历史；纠错也没有按设计串行执行 |
| 4 | `events()` 与 `start()` 之间存在竞态 | UI 可能收不到「聆听中」，界面卡在空闲状态 |
| 5 | 没填 Key 时走模拟云 | 「纯云端」每句都输出「这是云端流式模拟结果」 |
| 6 | 云纠错只在句末补「。」；WebSocket 解析 `payload.output.text`（正确字段是 `output.sentence.text`），不等 `task-started`，也不发 `finish-task` | 混合 / 云端模式实际不可用 |
| 7 | Apple Speech `requiresOnDeviceRecognition = false`；FluidAudio 在 `prepare` 时从 Hugging Face 下载 | 「纯离线」模式会把音频发往 Apple 服务器，或在录音开始时悄悄联网 |
| 8 | FluidAudio 用默认 `textNorm = 15`（woitn） | ANE 纠错输出没有标点、没有逆文本规整 |
| 9 | 模型下载 `for try await b in bytes` 逐字节迭代、整包读进内存，bz2 整块解压并且缓冲区按倍数重试 | 1.0–1.4 GB 的压缩包在 iPhone 上必然 OOM；tar 解包不拒绝 `../` |
| 10 | 判句固定能量阈值 0.01，没有最长句限制，固定裁掉尾部 0.625 s | 风扇噪声下永远不断句；强制断句时会砍掉真实语音 |
| 11 | API Key 明文存在 UserDefaults | 违背设计文档的 Keychain 要求 |
| 12 | 设置项互相重叠（`qualityProfile == .accurate` 会盖掉「高精度纠错」开关） | 开关不起作用 |
| 13 | 噪声经纠错得到「。」也会定稿 | 历史里出现只有标点的句子（用户数据里实际存在） |
| 14 | iOS 首页只有一条 44pt 工具栏；macOS 上 `onDelete` 不可用 | iOS 首屏空白；macOS 无法删除会议 |
| 15 | 沙盒下 `homeDirectoryForCurrentUser` 指向容器 | 旧模型迁移代码实际是空操作 |

## 2. 新架构

```
Apps/Yuyin (SwiftUI, @Observable)
  AudioCapture ──AsyncStream (有序)──▶ Recorder ──▶ TranscriptionSession (YuyinCore)
                                           │            ├─ UtteranceSegmenter（VAD + 断句）
                                           │            ├─ StreamingASREngine（同步返回 partial）
                                           │            └─ 串行纠错队列 → CorrectorASREngine (+ 混合备用)
                                           ▼
                                     MeetingLibrary ── MeetingStore（每条记录一个目录：meeting.json + audio.wav）
  AppEngineProvider ── LocalEngines (YuyinLocal) / CloudEngines (YuyinCloud)
```

### 2.1 会话契约（`TranscriptionSession`）

- `ingest` 由唯一的消费者按采集顺序依次 `await` 调用。
- 时间戳按已送入的样本数换算（音频时间，不含暂停时长），与 `audio.wav` 的偏移一一对应。
- 流式引擎的 `accept` **同步返回** `StreamingUpdate { text, isEndpoint }`，没有回调，所以不会出现迟到的 partial。
- 句子关闭后进入 `AsyncStream` 任务队列，由单个 worker 串行纠错。
- `stop()` = 关闭当前句 → 结束队列 → 等 worker 排空 → 关闭引擎 → 封装 WAV → 结束事件流。返回时所有句子都已定稿或标记失败。
- 事件流在 `init` 中创建（`AsyncStream.makeStream`），订阅晚了也不会丢事件。
- `pause()` 会先关闭当前句，同一句话不会被暂停切成两半。
- 只含标点的结果会被移除（`TextFilter.isMeaningful`）。

### 2.2 断句（`UtteranceSegmenter`）

- 以 20 ms 为一帧做能量 VAD。噪声底用最小值统计法：取最近 3 s 内最安静的帧；开头 0.5 s 快速校准；处于语音段内时上升很慢。
- 断句条件：静音达到 `silenceMs`、引擎自身报端点，或单句达到 `maxUtteranceSeconds`（切分处前后连续，不丢样本）。
- 送去纠错的音频是「首个有声帧前 300 ms → 最后有声帧后 200 ms」，即精确裁掉尾部静音。
- 结果与分块大小无关（有单测验证）。

### 2.3 引擎选择

| 模式 | 实时 | 纠错 | 备用 |
|------|------|------|------|
| 纯离线 | Sherpa Zipformer / 本机 Apple Speech | 本机模型 | — |
| 混合 | 同上 | Fun-ASR 同步 HTTP（句级 WAV） | 本机模型 |
| 纯云端 | Fun-ASR 实时 WebSocket | Fun-ASR 同步 HTTP | — |

- 「自动」纠错的优先级：FireRed（仅 macOS，需主动下载）→ SenseVoice·ANE → SenseVoice（Sherpa）→ Paraformer → 不纠错。
- 明确选择了某个模型但未安装时，直接报错，不静默降级。
- 云端模式没有 Key 时立即报错。生产代码里没有任何模拟引擎。
- Apple Speech 始终使用 `requiresOnDeviceRecognition = true`；设备不支持离线识别时报错。
- `EnginePlan` 与真正构建引擎走同一套解析逻辑，所以 UI 上显示的就是实际运行的。

### 2.4 模型

- `URLSession` 直接下载到文件 → 流式 bz2 + tar 解包到临时目录（1 MB 缓冲，内存恒定；支持 pbzip2 多段流、GNU / pax 长路径；拒绝绝对路径和 `..`）→ 校验 → 替换到位。取消或失败都不会留下半成品。
- SenseVoice 改用官方 int8 包（163 MB，原为 1.0 GB，模型相同）。
- SenseVoice·ANE 在设置里显式下载，下载后立即预热编译（首次约 90 s，之后 0.2 s）。会话中只从磁盘加载。
- sherpa 遇到损坏模型会直接 `fatalError`，所以创建识别器前先检查文件。
- 支持「导入已下载的模型文件夹」（Files / 访达，安全作用域 URL）。

### 2.5 数据

- `Meetings/<id>/meeting.json` + `audio.wav`（16 kHz 16-bit，约 1.9 MB/分钟）。
- 录音开始时先写一条 `isRecording = true` 的草稿，每次有句子定稿后 2 s 内自动保存。崩溃后下次启动标记为「意外中断」，已识别的内容保留。
- WAV 读取不依赖文件头里的长度，未封装的文件也能读。
- v0.1 的 `meetings.json` 首次启动时导入（跳过只含标点的记录），原文件改名为 `meetings.migrated.json`。
- v0.1 设置迁移：明文 `apiKey` 转存到钥匙串并从 UserDefaults 中清除；旧开关映射到新的引擎选择。

### 2.6 界面

- `NavigationSplitView`：侧栏是「实时转写」和历史记录（支持搜索、重命名、删除）；详情是录音页或记录页。macOS 和 iPad 默认打开录音页，iPhone 首页是列表。
- macOS 有独立的设置窗口（⌘,），菜单里有 ⌘R 开始 / 停止、⇧⌘P 暂停；iOS 设置以 sheet 打开。
- 记录页提供说话人筛选、搜索、导出（txt / SRT / Markdown 文件）、复制、整场多人分析（基于保存的录音）。
- iOS 录音时保持亮屏，系统中断（来电等）时自动暂停；输入设备变化时自动重建音频链路。

## 4. v0.3 新增（同日）

用户新需求：横条首页、录音中多人识别与命名、录音完成后导出、实时翻译、支持腾讯会议等会议软件 / 网页 / 其他 App。

### 4.1 界面
- **macOS**：首页是一个无边框横条窗口（开始录音 · 音源 · 录音记录 · 设置），默认悬浮在最前（可在设置中关闭）。录音时横条下方弹出面板，显示状态、说话人名单和最新两句（含译文）；结束后显示「已保存」卡片，可直接导出或查看记录。录音记录和设置是独立窗口。
- 横条窗口是 borderless，所以不会多出标题栏的安全区，窗口高度正好等于内容高度。代价是它不能成为 key window：命名输入放在 popover 里，快捷键放在菜单里（⌘R 开始 / 结束、⇧⌘P 暂停、⌘L 录音记录）。面板展开时窗口向下长，顶边保持不动（已实测）。
- **iOS**：同样的横条和面板放在顶部，录音记录和设置以 sheet 打开。窄屏时「录音记录 / 设置」只显示图标。

### 4.2 多人识别与命名
- `SpeakerBook`（YuyinCore）：命名；与已有名字相同则合并（别名映射）；按句改派说话人；分配新说话人。录音中和录音后用的是同一套逻辑。
- 记录里保存 `speakerNames`；导出使用这些名字。整场分析（pyannote）重新编号后，按多数投票把原来的名字迁移到新编号（`SpeakerMapping.transferNames`）。
- 默认开启（需要「说话人声纹」模型；没有模型时面板里直接提供下载按钮）。未定稿的句子显示「…」，说话人在定稿时判定。

### 4.3 实时翻译
- `TextTranslator` 协议；会话里有一条**独立的翻译队列**，不拖慢纠错；`stop()` 会等翻译也完成。翻译失败只出一次提示，不影响定稿。
- 方向：「自动」时中文译英文、其他语言译中文（按文字的书写系统判断）；也可以指定目标语言。
- 引擎：系统离线翻译（Apple Translation，`TranslationSession(installedSource:target:)`，macOS 26 / iOS 26）或通义千问 MT（`qwen-mt-flash`，OpenAI 兼容接口）。「自动」规则：纯离线模式 → 系统翻译（不会联网）；混合 / 云端模式 → 千问 MT。
- 译文保存在 `Utterance.translation`，导出时可选是否包含。

### 4.4 会议软件、网页和其他 App 的声音（macOS 14.2+）
- `SystemAudioSource`：`CATapDescription` + `AudioHardwareCreateProcessTap` + 私有聚合设备 + IOProc。「系统声音」采集除本 App 外的全部声音；「指定应用」按 Bundle ID 匹配该应用及其辅助进程（如 `com.google.Chrome.helper`）。
- 「会议」模式：麦克风（开启 Voice Processing 回声消除，并关闭对其他声音的压低）+ 系统声音，由 `AudioMixer` 逐样本相加；任一路停顿超过 400 ms 时，另一路直接透传。
- 连续 8 秒收到的都是纯数字静音时，提示检查「录制系统音频」权限。
- iOS 不允许采集其他 App 的声音。要支持，需要 ReplayKit 广播扩展（后续）。

### 4.5 实测（本机，真实模型）
- 系统声音端到端：用 `afplay` 播放中文、英文、中文三段 → 「开放时间早上9点至下午5点。」/「The tribal chieftain…」/ 第二次的中文；说话人依次为 0 / 1 / 0；译文方向分别为 中→英 / 英→中 / 中→英。
- 测试中发现并修复一个 bug：sherpa 的「静音端点」（规则 1）因解码延迟，会落在新句子刚开口时，把它切成 0.3 s 的碎片。现在端点只在已有文字时才切句（有回归测试）。
- 对比测试：SenseVoice 的语种设置保持为中文，因为中文模式同样能正确识别英文整句，而自动模式会把短句中文识别错。

## 5. v0.4：识别效果与界面统一（同日）

用户反馈：①识别效果不好；②界面不统一，「设置」「录音记录」应和实时面板一样做成向下展开的卡片。

### 5.1 识别：用真实录音定位问题
在用户本机的两段真实录音（`Meetings/*/audio.wav`，笔记本麦克风，语音约 −40 dBFS）上离线重放（`EvaluationTests`，默认跳过）：

1. **断句是主因之一**：能量 VAD 一直没检测到停顿（静音里零星的 20 ms 尖峰不断打断计时），25 秒才强制切一刀，实际断句靠 sherpa 引擎的端点，边界不准，还把大段静音包进句子。
   - 修复：100 ms 平滑 + 滞回（进入门槛 3 倍噪声底，维持门槛 2.5 倍）+ 连续 3 帧才算开口；噪声底改用 20% 分位数；开头 1.5 s 快速校准。修复后两段录音的切分点都和说话的句子对齐。
   - 评估过 Silero VAD：在低音量录音上会漏掉整句（「很模糊」），阈值调低又会把多句连成一段，因此不采用。
2. **纠错模型**（每句的原始音量和归一化音量各识别一次，实时率是在本机测得）：

| 模型 | 明显错字 | 实时率 | 噪声片段 |
|---|---|---|---|
| Paraformer-large 2023-09-14 | **约 3** | 0.014 | 输出乱码 |
| Fun-ASR-Nano 2025-12 | 约 4 | 0.07 | 编造内容 |
| SenseVoice·ANE | 约 7 | 0.008 | 「。」（正确） |
| Qwen3-ASR 0.6B 2026-03 | 很多 | 0.10 | 空（正确） |

   - 默认改为 **Paraformer-large**，并自动配 62 MB 的 CT-Transformer 标点模型。
   - 「自动」的顺序：Paraformer → FireRed → SenseVoice·ANE → SenseVoice。Fun-ASR-Nano 和 Qwen3-ASR 只作为可选项（支持热词）。
   - 注意：`paraformer-zh-int8-2025-10-07` 其实是四川话微调版本，不要用于普通话。
   - 新流式模型 `zipformer-zh-int8-2025-06-30` 在这些录音上反而会漏句，所以实时字幕仍使用 2023 中英模型。
3. **防幻觉**（`GuardedCorrector`）：实时字幕什么都没识别到时，先用 SenseVoice 确认确实有人说话；输出出现同字连续 4 次以上或零散字母时，回退到 SenseVoice 的结果。这样开头那声爆音被正确丢弃。
4. **逐句音量归一化**：按最响 30% 的帧估计语音电平，增益上限 12 倍且不削波。
5. **多人**：同一说话人的相似度，长句 0.6–0.73，短句只有 0.2–0.45；不同说话人 ≤ 0.38（用官方样例实测）。改为：加入阈值 0.40，与按时长加权的平均声纹比较；有效语音不足 1 秒的句子不能新建说话人；识别结果为空的片段不参与聚类。重放后，两段录音里同一个人的所有句子都归为同一说话人（之前「很模糊」被误判为第二个人）。

重放结果对比：「很多人去识变吗」→「他不能多人去识别吗？」；「是多语字，而且这两个……」→「而且这两个说话人明明是同一个说话人。」；「体高高」→「提高高」；爆音被丢弃；之前漏掉的「真搞笑」被找回。

### 5.2 界面：一个横条 + 一张下拉卡片
- 「实时字幕」「录音记录」「设置」都是横条下方的同一种卡片（`PanelKit`：卡片、分组、行、胶囊按钮、搜索框、转写行）；横条按钮负责打开和收起。录音中打开其他卡片时，横条上会出现一个按钮，点一下回到实时字幕。
- 录音记录：列表 → 详情（返回、导出、更多），改名和删除都在卡片内完成。设置：常用 / 识别 / 模型 / 云端 四个分页。
- macOS：横条改为自建的 `NSPanel`（无边框、悬浮、`nonactivatingPanel`、可成为 key）。卡片里的输入框可以打字，点按钮也不会抢走会议软件的焦点。导出、导入使用独立的系统面板。实测展开卡片时顶边固定，窗口向下长。
- 修复一个渲染问题：材质背景上的滚动视图里，层级样式（`.secondary`，包括 `Color.secondary`）会失去对比度，改用系统的 `secondaryLabel` 颜色。

## 6. v0.5：连续音频丢内容、中英文识别、展开记录（同日）

用户用视频声音实测（中文科技视频夹杂英文产品名、英文对话视频）后反馈：显示的内容很少、和识别的不一样；英文识别很差；希望录音中能展开会议记录。

1. **严重 bug：连续音频大量丢内容**。视频里人声叠着背景音乐、几乎没有停顿，v0.4 的 VAD 把整段判成「底噪」，把音频当静音丢掉，只把最后 0.6 秒送去纠错，结果纠错文字覆盖了长长的实时字幕（例如十几秒的内容只剩「呃，灵动的小舞修服。」）。
   - 修复：分段器改为**连续切分**，每段从上一个断点一直覆盖到这一个断点，中间音频一律保留（新增回归测试「每个样本恰好属于一个片段」）。只有 VAD 和实时识别都判定没人说话时，才丢弃前导空白（保留最近 2 秒）。
   - 长时间连续的音频，在单句上限（默认改为 15 秒）前 3 秒内最安静的位置切；sherpa 的句末静音判定从 1.2 秒改为 1.0 秒。
   - 字数校验：纠错结果的内容量不到实时字幕的一半时，判定为纠错失败，退回更完整的版本。
2. **中英文**：Paraformer-large 是纯中文模型，英文会被识别成中文（「YOUR JOB OH MY GOD」→「哥，来玩，问问你……」）。在两段视频上重新对比：
   - 英文：Fun-ASR-Nano 最好（大小写、标点都对），SenseVoice 英文模式其次，Paraformer 不可用。
   - 中英混说：Fun-ASR-Nano 最好（homepod、apple TV、homepod mini）；FireRed 中文很好，但会编造英文内容，而且太慢（实时率 0.4）；Paraformer 英文部分差。
   - 口语中文：Fun-ASR-Nano 与 Paraformer 接近。
   - 结论：macOS 的「自动」改为 **Fun-ASR-Nano 优先**，iOS 仍以 Paraformer 为主；使用 Paraformer 时，实时字幕判定为英文的句子交给 SenseVoice 英文模式（`LanguageRoutingCorrector`）。
   - SenseVoice 中文模式下的短英文句会被转成中文，英文模式则正常（「Could you show us something?」）。
   - 全大写英文（流式模型和大模型偶尔输出）自动转成句首大写的正常格式。
3. **展开会议记录**：实时卡片上增加「展开」按钮，展开后卡片变宽（macOS 760）、变高（约屏幕高度的 75%），显示完整的滚动转写，含说话人和译文，自动跟随最新一句。「翻译中…」只对确实需要翻译的最近几句显示。

## 7. v0.6：界面重新设计（同日）

目标：简洁、美观、大方。整体改成一套深色 HUD 风格，两端共用。

- **设计语言**（`Theme`、`PanelKit`）：深色半透明材质（`ultraThinMaterial` + 深色叠层 + 细描边 + 柔和阴影）；一个强调色（珊瑚红，用于录音按钮、主按钮、开关）；译文用天蓝色；说话人用一组低饱和的颜色；正文统一白色的三级透明度（主 / 次 / 弱），不再混用系统层级色。字号、圆角、间距都收在 `Theme` 里。
- **横条**：左边是录音按钮（录音时有呼吸光环），空闲时显示「开始录音」和音源 / 模式菜单（「麦克风 · 纯离线 ⌄」），录音中显示计时、波形和暂停；右边只有「录音记录」和「设置」两个图标按钮，当前打开的卡片对应的按钮会高亮。
- **卡片**：实时字幕、展开记录、已保存、录音记录、设置都使用同一种卡片：标题行（`CardHeader`）、分组（`SettingsGroup` / `SettingsRow`）、胶囊按钮（`HUDButtonStyle`）、搜索框、转写行（`TranscriptRow`）。设置的四个分页和「模式」使用同一个分段控件（`TabSwitcher`）。
- **控件自绘**：macOS 上不是 key 的面板里，系统开关的「开」会变成灰色，只能靠滑块位置分辨，所以开关和步进器（− / +）改为自绘，两端外观一致。
- **说话人**：圆点 + 名字（`SpeakerName`）；正在识别、还没有说话人的句子显示「识别中」（圆点轻微闪烁）。
- **macOS 面板**：
  - 修复：录音按钮的呼吸动画原来在 `onAppear` 里用 `withAnimation(.repeatForever)` 启动，会把同一时刻的布局变化也卷进无限循环动画，导致整个面板（包括横条）上下错位。改用只作用于光环本身的 `phaseAnimator`。
  - 内容固定在窗口顶部，窗口尺寸跟上之前横条也不会移动。
  - 位置改为自己保存「顶边 + 水平中心」。原来的 `setFrameAutosaveName` 对不可缩放的窗口只恢复原点，展开过宽卡片后，下次启动会偏到左边。
  - 去掉面板出现时的系统动画。
- **验证**：iPhone 模拟器截图；macOS 用 DEBUG 参数 `-YuyinSnapshot <png>` 让面板自己渲染成图片（不需要屏幕录制权限），配合 `-YuyinDemo live|done`、`-YuyinExpanded 1`、`-YuyinPanel history|settings`、`-YuyinSettingsTab recognition|models|cloud` 检查每个状态。窗口位置和尺寸用 `CGWindowListCopyWindowInfo` 确认。

## 8. v0.7：断句、日语和阴影（同日）

用户反馈：界面有明显的黑色轮廓；中文停顿稍长就被拆成两句；识别结果里出现日语。用最新一条录音（4 分钟游戏解说，夹着广告口播）定位：

1. **日语来自 Fun-ASR-Nano**。62 句里有 7 句是日语，全都出在零点几秒的短碎片上：实时字幕是「这波」「哎哟」「一」，纠错结果却成了「ちょっと。」「ええよっ！」「いい。」。这是多语种模型在没有限定语言时，对短促、带音效的片段乱猜。
   - Fun-ASR-Nano 改用「语音转写成中文：」提示（sherpa-onnx `language: "中文"`）。实测：游戏录音里的日语从 2 处降到 0；英文视频仍然输出英文，没有被翻译，只是标点变成全角，所以以英文为主的句子把全角标点换回半角（`TextFilter.normalizePunctuation`）。
   - 运行中切换提示语言的方案走不通：sherpa-onnx 1.13.8 的 Fun-ASR-Nano 实现类自己又声明了一份 `config_`，`SetConfig` 改的是基类那份，对它不生效。
   - 兜底：任何纠错结果里出现日文假名或韩文，都按幻觉处理，退回 SenseVoice 或实时字幕（`TextFilter.looksHallucinated`）。
2. **断句**。被切开的地方有两类：
   - 流式模型 1 秒内没解码出新字就判定句末，哪怕人还在出声（拖长音、游戏音效）。现在必须分段器也听到一段停顿，这个判定才生效；已经超过 8 秒的长句例外，因为连续的背景音乐里分段器永远听不到停顿（`SegmenterConfig.endpointSilenceMs` / `endpointBackstopMs`）。
   - 说了一两秒就停下，多半是话还没说完（「他应该学的是 / E技能」「先来把一刀 / 斩」），但 0.7 秒的停顿就把它切开了。现在人声不到 2 秒的短句要停 1.3 秒才结束，长句仍是 0.7 秒（`shortSentenceMs` / `shortSentenceSilenceMs`）。日语恰好出在这些碎片上，合回整句后也就不会被单独拿去乱猜。
   - 结果（按实时字幕统计，不纠错）：游戏录音从 60 句降到 46 句，极短碎片（不超过 3 个字或词）从 20 个降到 9 个；中英混说视频从 17 句降到 11 句，碎片从 5 个降到 1 个。加上纠错后，游戏录音最终 47 句，原来是 62 句。
   - 试过但没采用：用「流式模型出了新字」重置静音计时。它修好了广告里「都怎么 / 处理」这种词中间的切分，但会把快节奏的多人英文对话合成 13 秒的大段，不同说话人混进同一句。
   - 评测：`testSessionReplayWithCorrector` 新增 `YUYIN_EVAL_SILENCE`、`YUYIN_EVAL_ENDPOINT_SILENCE`、`YUYIN_EVAL_BACKSTOP`、`YUYIN_EVAL_SHORT`、`YUYIN_EVAL_SHORT_SILENCE`，并输出每句前的停顿和汇总（句数、极短碎片、最长句）。`YUYIN_EVAL_CORRECTOR=funasr-zh` 是中文提示的 Fun-ASR-Nano。
3. **黑色轮廓**。卡片和横条的阴影（黑色 32% 不透明、半径 18、下移 8）伸出约 26pt，而 macOS 窗口四周只留了 16pt，阴影在窗口边缘被截断，显出一圈黑框。窗口快照最外圈像素的不透明度实测高达 26/255。现在阴影改为 25% 不透明、半径 10、下移 4，边距改为 24pt，最外圈的不透明度降为 0；边缘描边稍微提亮，是一条浅色细线。

## 9. v0.8：多人识别（2026-10-12）

用户反馈：不是同一个人说的话被标成同一个人；分不出多个说话人。最新的一条英文访谈（主持人 + 受访者）里，每句都是「说话人 1」。

**评测方法**。用户的录音没有标准答案，所以用了两种数据：
- 用户录音里能确定身份的人：游戏主播、广告配音、科技视频主持人、用户本人、访谈两人；
- 公开的 AMI 会议语料 ES2004a、IS1009a：真实的 4 人会议，共约 31 分钟，带逐句说话人标注（RTTM）。

评测按产品流程回放（断句 → 每句提取声纹 → 在线聚类），统计说话人准确率（簇与人一一对应后，按时长计）、分出的人数，以及混进不止一个人的句子比例（`testSpeakerReplay`、`testSpeakerClusteringLab`、`testSpeakerModelComparison`、`testReanalyzeMeeting`）。

**找到并修复的问题**（两场 AMI 会议的准确率）：
1. 声纹用的是整段音频，而分段是连续的，一段的开头可能是几秒静音、音乐或上一个人的尾音。现在只用这句的人声部分（前后各 0.1 秒）。用 CAM++ 时，准确率从 57.0% / 86.9% 提到 95.5% / 90.3%；整段输入会把不同的人并到一起，4 个人只分出 3 个。
2. 聚类器根据「这句有多少人声」决定能否新建说话人（满 1 秒才行），而传进去的是 VAD 统计的响亮帧时长。远场、轻声和系统内录的声音会被严重低估，于是几乎所有句子都不能新建说话人，只要相似度超过 0.2 就并进已有的人。现在用人声部分的实际时长。用原模型回放时，ES2004a 从 61.4% 提到 92.4%（IS1009a 从 85.9% 变为 81.2%，原模型在这场本来就不稳）。
3. 声纹模型换成 CAM++（3D-Speaker，中英通用，28 MB），取代 ERes2Net（40 MB）。CAM++ 在用户录音上区分不同人的等错误率是 4.9%（原来 7.8%），AMI 上的准确率为 95.7% / 90.1%，速度快一倍。ERes2NetV2 在 AMI 上不稳定（常把所有人并成一个），WeSpeaker ResNet34 在用户录音上基本失效（等错误率 38%）。已装旧模型的用户启动后会自动下载新模型。
4. 聚类参数按 CAM++ 重新标定：加入阈值 0.5；人声不少于 2 秒才能新建说话人（1 秒时 4 个人会分成 8～9 个）；短句与已知的人相似度低于 0.35 就不标，宁缺毋错；短句并入的门槛随长度放宽，4 秒以上为 0.5，2 秒为 0.4，因为同一个人两秒的话很难达到 0.5。最终 ES2004a 4 个人分出 5 个，准确率 95.7%。
5. 「重新分析说话人」原来用 pyannote 整场分割加聚类，在 AMI 上只有 34%～91%（阈值 0.5 时分出 24～32 个「人」），比实时标注还差。现在改为按时间顺序，对每句的人声重新提取声纹、用同样的聚类重新分一遍。不再需要「说话人分割」模型；旧录音也能用新模型修正。

**试过但没采用**：在句子内部用 pyannote 找换人点再切开。混杂率反而从 28% 升到 36%，准确率也下降，因为切点对不准，切出来的片段又短。约四分之一的句子仍混有不止一个人（AMI 里抢话、附和很多），这是只按停顿断句的上限。

**局限**：两三秒的短句声纹仍然不稳。访谈里主持人的两句短话被分成了两个人，可以给两人起同一个名字来合并。
